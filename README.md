# Streaming Platform Data Engineering Pipeline

An end-to-end data engineering pipeline for a streaming-platform analytics
use case using **Amazon S3, Snowflake, and dbt**.

The project uses the **MovieLens 20M dataset** as a representative source
dataset to simulate a streaming-platform environment and builds an
analytics-ready dimensional warehouse for content and user engagement
analysis.

> MovieLens is used as a public representative dataset. This project does
> not use or represent proprietary Netflix data.

---

## Project Overview

The objective of this project is to build a complete analytical data pipeline
from cloud-based source files to a tested dimensional warehouse.

The pipeline covers:

- Cloud-based source ingestion
- Snowflake data loading
- dbt-based transformation
- Dimensional data modeling
- Incremental processing
- Data quality testing
- Analytical metric generation
- Documentation of modeling and engineering decisions

The project is intentionally scoped as a **production-inspired portfolio
project**, rather than an attempt to reproduce a production streaming
platform architecture.

## Business Scenario

The dataset is treated as if it were generated by a streaming platform that
needs to understand content performance and user engagement.

The analytical layer is designed to support questions such as:

### Content Performance

- Which movies receive the most ratings?
- Which movies have the highest or lowest average ratings?
- How does rating activity change over time?

### User Engagement

- Which users are most active?
- How many movies has a user interacted with?
- How does user rating behavior vary?

### Genre Performance

- Which genres receive the most engagement?
- Which genres have the highest average ratings?
- How does genre engagement change over time?

### Content Characteristics

- Which genome tags are strongly associated with movies?
- Which content characteristics are associated with highly rated movies?

### Time-Based Analysis

- How does rating activity evolve over time?
- Which movies show sustained or increasing engagement?

## Data Pipeline

### 1. Source

MovieLens 20M provides:

- Movie metadata
- User ratings
- User-generated tags
- Genome tags
- Genome relevance scores
- IMDb/TMDB identifiers

The source files are uploaded to an Amazon S3 bucket.

### 2. Raw Layer

Snowflake reads the source files from S3 through:

- Snowflake Storage Integration
- AWS IAM role
- External stage
- CSV file format
- `COPY INTO`

The raw layer preserves the source structures with minimal transformation.

### 3. Staging Layer

dbt staging models provide lightweight source standardization:

- Rename source columns to analytics-friendly names
- Convert Unix timestamps to Snowflake timestamps
- Preserve source-level grain
- Establish a consistent interface for downstream models

The staging layer is intentionally kept simple.

### 4. Mart Layer

The mart layer contains the analytical dimensional model.

```text
MARTS
│
├── Dimensions
│   ├── dim_movies
│   ├── dim_users
│   ├── dim_genres
│   └── dim_genome_tags
│
├── Facts
│   ├── fct_ratings
│   ├── fct_movie_tags
│   └── fct_genome_tag_relevance
│
├── Bridge
│   └── bridge_movie_genres
│
└── Metrics
    └── movie_rating_metrics
```

## Dimensional Model

The model follows dimensional modeling principles, with each model having a
defined grain and analytical purpose.

### Dimensions

| Model             | Grain                     | Purpose                                 |
| ----------------- | ------------------------- | --------------------------------------- |
| `dim_movies`      | One row per movie         | Movie metadata and external identifiers |
| `dim_users`       | One row per observed user | User-level analytical entity            |
| `dim_genres`      | One row per genre         | Normalized genre reference              |
| `dim_genome_tags` | One row per genome tag    | Content characteristic reference        |

### Fact Tables

| Model                      | Grain                               | Purpose                                  |
| -------------------------- | ----------------------------------- | ---------------------------------------- |
| `fct_ratings`              | One rating event                    | Primary user-content engagement event    |
| `fct_movie_tags`           | One user tag event                  | User-generated content metadata/activity |
| `fct_genome_tag_relevance` | One movie × genome-tag relationship | Content characteristic relevance         |

### Bridge

| Model                 | Grain                          | Purpose                                            |
| --------------------- | ------------------------------ | -------------------------------------------------- |
| `bridge_movie_genres` | One movie × genre relationship | Resolves the many-to-many movie/genre relationship |

### Analytical Mart

| Model                  | Grain                     | Purpose                              |
| ---------------------- | ------------------------- | ------------------------------------ |
| `movie_rating_metrics` | One movie × calendar date | Daily movie-level rating performance |

Detailed modeling rationale and design decisions are documented in
[`docs/dimensional-model.md`](docs/dimensional-model.md) and
[`docs/design-decisions.md`](docs/design-decisions.md).

## Incremental Processing

`fct_ratings` is implemented as an incremental dbt model.

New records are identified using the maximum `rating_timestamp` already
present in the target model.

This demonstrates incremental ELT processing without introducing unnecessary
complexity for a static public dataset.

The implementation currently uses a timestamp watermark. As a result,
late-arriving records with timestamps older than the existing watermark would
require a different loading strategy.

This limitation is documented intentionally rather than hidden.

## Data Quality

Data quality is treated as part of the transformation process.

### Generic dbt tests

The project includes:

- `not_null`
- `unique`
- `relationships`

These validate model-level assumptions and referential integrity.

### Singular business tests

Custom tests validate business-specific rules including:

- Ratings must fall within the expected `0–5` range.
- Genome relevance scores must fall within `0–1`.
- Movie/genre relationships must be unique.
- Daily movie rating metrics must maintain their defined grain.
- Aggregated rating metrics must reconcile to the underlying rating facts.

The current dbt build completes successfully with:

```text
PASS=72
WARN=0
ERROR=0
SKIP=0
```

## Key Engineering Decisions

Some of the main design decisions include:

- Keeping raw, staging, and mart layers physically separated.
- Using dbt staging models for source standardization rather than business
  transformations.
- Modeling movies and genres separately because a movie can belong to
  multiple genres.
- Using a bridge table to resolve the movie/genre many-to-many relationship.
- Treating ratings and user tags as event-oriented facts.
- Keeping genome tags separate from user-generated tags because they represent
  different concepts.
- Enriching the movie dimension with IMDb and TMDB identifiers rather than
  creating a separate link dimension.
- Materializing repeated analytical aggregations as tables rather than
  recalculating them through views.
- Using incremental processing for the primary rating fact.
- Evaluating dbt snapshots but deliberately excluding them because the source
  data does not present a meaningful mutable-record history requirement.

The reasoning behind these decisions is documented in
[`docs/design-decisions.md`](docs/design-decisions.md).

## Scope and Limitations

This project is intentionally scoped.

It does not attempt to demonstrate:

- Real-time streaming
- Kafka
- Spark
- CDC
- Complex SCD Type 2 processing
- Infrastructure as Code
- Enterprise security architecture
- Production-scale orchestration

The purpose is to demonstrate a coherent batch-oriented cloud ELT pipeline,
dimensional modeling, incremental processing, and data quality practices
without introducing technologies that are not required by the use case.
